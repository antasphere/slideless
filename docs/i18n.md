# Dashboard i18n (en/fr)

The dashboard UI is bilingual: English and French. The system is
deliberately tiny — two statically imported message catalogs, one `t()`
function, zero runtime dependencies (see [ADR 007](decisions/007-dashboard-i18n.md)
for the tradeoff).

## How it works

Everything lives in `apps/dashboard/src/lib/i18n/`:

| File       | Role                                                                                                                                   |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `en.ts`    | The English catalog and the **source of type truth**: `export const en = {...} as const` + `export type MessageKey = keyof typeof en`. |
| `fr.ts`    | The French catalog, typed `Record<MessageKey, string>` — a missing **or** extra key is a compile error.                                |
| `index.ts` | `LANGS`, `resolveLocale()`, `getLocale()`, `initLocale()`, `setLocale()`, and `t(key, params?)`.                                       |

Key properties:

- **The locale is fixed per page load.** The root `+layout.ts` calls
  `initLocale()` once before anything renders (it also sets
  `document.documentElement.lang`). Switching language persists the choice
  to localStorage (`platform.lang`) and does `window.location.reload()`.
  Because the locale can never change mid-page, `t()` is a plain
  synchronous function — no stores, no runes, no reactivity plumbing.
- **Resolution order:** localStorage `platform.lang` → browser language
  (`navigator.language` starting with `fr`) → English.
- **No URL prefixing.** The dashboard is a pure SPA behind auth with no SEO
  surface, so there is no `/fr/...` route segment; localStorage persistence
  is the whole story.
- **Interpolation:** messages carry `{name}` placeholders,
  `t('invite.joinTitle', { workspace: 'Acme' })`. Unknown placeholders are
  left intact rather than rendered as `undefined`.
- **Fallback chain:** active locale → English → the key itself. The first
  two are guaranteed complete at compile time; the chain is belt and
  braces.
- **Formatters follow the UI language.** `lib/format.ts` passes the app
  locale to `toLocaleDateString`/`toLocaleString`, localizes relative
  times ("5m ago" / "il y a 5 min"), and localizes byte units (KB/Ko).
- The switcher (`lib/components/shared/LanguageSwitcher.svelte`) appears in
  the NavUser dropdown inside the app and fixed top-right on every public
  page (login, setup, forgot/reset password, invite, OAuth consent).

## What is NOT translated (by design)

- **Server-originated error messages.** The API responds in English; when
  the dashboard surfaces `e.message` from a `PlatformApiError` (or a Better
  Auth error), it passes through untranslated. Only client-side fallbacks
  and status-code messages (401/403/429 ladders) are localized. Translating
  server messages would mean shipping error-code→message maps for every
  endpoint — out of scope for the template.
- **Transactional emails** (`apps/server/src/email/templates.ts`) are
  English-only. Proper email localization needs a per-user locale column
  (Better Auth schema territory) and is listed as an open item in
  `production-readiness.md`.
- **Data values**: role names (`owner`/`admin`/`member`), scope ids
  (`presentations:read`), auth-method slugs, audit action codes, and the
  `actorVia` values render as-is — they are API vocabulary, not UI copy.
- **Load-bearing literals and sample values**: the type-`DELETE`-to-confirm
  token stays `DELETE` in every language (the check is an exact string
  match); the `ci-deploy` key-name and `Acme Platform` instance-name
  placeholders are sample values, not prose, and stay as-is. Sample email
  placeholders (`teammate@example.com`) ARE localized.

## Guarantees and tests

- Compile time: `fr.ts` fails to build on a missing or extra key.
- `src/lib/i18n/i18n.test.ts` (vitest): en/fr key-set equality (guards an
  `as any` regression on the fr export), `{placeholder}` token parity per
  key, no empty strings, `t()` interpolation behavior.
- `e2e/smoke.spec.ts` (Playwright, real compose stack): switch to FR on the
  login page, assert a French string, reload, assert persistence and
  `<html lang="fr">`.

## Adding a message

1. Add the key to `en.ts` (flat, dot-namespaced: `page.thing`).
2. The compiler now forces the same key in `fr.ts` — write real French, not
   machine-literal (French typography in `fr.ts` uses U+2019 apostrophes
   and U+00A0 non-breaking spaces before `?` `!` `:` `;`).
3. Use it: `t('page.thing')` or `t('page.thing', { name: value })`.

## Adding a locale (recipe)

1. Create `apps/dashboard/src/lib/i18n/de.ts`:

   ```ts
   import type { MessageKey } from './en';
   export const de: Record<MessageKey, string> = {/* every key — the compiler enforces it */};
   ```

2. In `index.ts`: add `'de'` to `LANGS` and `de` to the `catalogs` map.
3. Optionally extend `resolveLocale()`'s browser-language sniff.
4. The switcher, tests, and `<html lang>` pick the new locale up
   automatically (the i18n unit test iterates the catalogs it imports — add
   `de` to its `catalogs` map to cover it).
5. **Read ADR 007 first**: past ~3 locales, reconsider static imports
   (every locale ships in the bundle) in favor of dynamic per-locale
   imports or Paraglide.
